# Flywheel turn 1 (qwen3:14b) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Generate an applier-verified, contamination-guarded training corpus of ideal read→patch→done trajectories, QLoRA-tune qwen3:14b on it, convert to GGUF, and let the unamended G4 gate decide.

**Architecture:** Spec `docs/superpowers/specs/2026-08-16-flywheel-14b-design.md` (Brice-approved). The load-bearing principle: every training prompt and every verification runs through the SERVING code via a new `flywheel-tool` bin (thin pub wrappers over the real `render_prompt`/transcript formatting/`land()` — no second implementation anywhere). A seeded, deterministic Python factory generates NEW tasks; the corpus is reproducible from (code, seed) and only its fingerprint is committed.

**Tech Stack:** Rust (the tool bin, in-workspace), Python 3 (factory, `tools/flywheel/`), unsloth + TRL QLoRA in a dedicated venv, llama.cpp converter/quantizer.

## Global Constraints

- Contamination is voided by design (spec §3): the corpus shares NO goals, file contents, target filenames, or search strings with `codec-tasks-v1`; a machine comparator proves it and its output is committed BEFORE training.
- Pre-registration (spec §6) is committed BEFORE any training step: success = the existing gate (≥80% = 16/20 under envelope-v3 on codec-tasks-v1); baseline 7/20; kill = tuned < 7/20 → adapter shelved, recorded; intermediate = recorded honestly, model stays demoted. No tune-and-rerun.
- Training completions are RAW (no chat template, matching serving): each completion ends exactly at `</action>` with NO trailing EOS token appended — v3's stop is the terminator at serving time, and an EOS habit would leak into v1/v2 behavior.
- The factory is seeded and deterministic: same (code, seed) → byte-identical corpus. The corpus JSONL is NOT committed; its SHA-256 + counts are.
- Rust: fmt + clippy `-D warnings` both feature sets, `cargo test --workspace` green, files ≤800 lines. Python: `python3 -m pytest tools/flywheel/tests` green; stdlib + declared deps only. NEVER wrap commands in the `timeout` binary. Conventional commits, no attribution footers.
- GPU discipline: no competing tenants at training/gating; detached (`setsid nohup` + pid file) for anything projected >2 h; never kill in-flight runs.
- New-subject discipline: the tuned model registers as `qwen3-14b-flywheel1`; the stock 14B's verdicts are untouched.

### Task 1: `flywheel-tool` — the serving-faithful render/verify bin

**Files:**
- Modify: `crates/bloomery-daemon/src/task/task_loop.rs` (two thin pub wrappers; the private internals move nothing)
- Create: `crates/bloomery-daemon/src/bin/flywheel_tool.rs`
- Test: `crates/bloomery-daemon/tests/flywheel_tool_test.rs`

**Interfaces:**
- Consumes: `render_prompt` (private — hence the wrappers), `record_step`'s transcript format, `bloomery_core::action::lens::{land, PlainText}`, `bloomery_core::action::PatchBody`, `bloomery_daemon::task::lens_py::PythonLens`, `EnvelopeLens` (config).
- Produces (Task 2's factory shells out to these):
  - `pub fn render_task_prompt(goal: &str, patch_codec: PatchCodec, envelope: EnvelopeLens, transcript: &str) -> String` — in task_loop.rs, implemented by building the same internal state `render_prompt` consumes (a doc comment pins: "this function and `render_prompt` MUST share one body; the wrapper constructs a minimal TaskSpec and calls the real function"). Implementation: build a `TaskSpec` with the given fields (grant/bounds/cwd/budget/max_steps are irrelevant to rendering — use empty/default values via the existing test-support constructors) and return `render_prompt(&spec, transcript)`.
  - `pub fn transcript_entry(step: u32, verb: &str, outcome: &str, content: &str) -> String` — extracted from `record_step`'s `push_str` (record_step now CALLS it; one source). Format, pinned today at task_loop.rs:~155: `"\n[step {step} {verb}] {outcome}\n{content}\n"`.
  - The bin `flywheel-tool` reads one JSON request per line on stdin, writes one JSON response per line on stdout:

```json
// subcommand "trajectory" (the only one the factory needs):
// request
{"cmd":"trajectory","goal":"...","patch_codec":"search_replace","envelope":"v3",
 "target":"stats.py","target_contents":"...file bytes...",
 "search":"...","replace":"...","summary":"one line"}
// response: the three SFT pairs, prompts rendered by the REAL code, patch land-verified
{"pairs":[{"prompt":"...","completion":"<action verb=\"read\" path=\"stats.py\">\n</action>"},
          {"prompt":"...","completion":"<action verb=\"patch\" path=\"stats.py\">\n<<<<<<< SEARCH\n...\n=======\n...\n>>>>>>> REPLACE\n</action>"},
          {"prompt":"...","completion":"<action verb=\"done\">\none line\n</action>"}],
 "landed":true,"patched_contents":"..."}
// "landed":false (with "landing_detail") when the reference does not land — the factory treats that as a fatal factory bug.
```

  - Pair construction inside the bin, pinned: pair 1's prompt = `render_task_prompt(goal, codec, envelope, "")`; pair 2's transcript = `transcript_entry(1, "read", &format!("read {} bytes", target_contents.len()), target_contents)` (byte-parity with `exec_read`'s uncapped outcome string at `task/exec.rs:~176` — cite it); pair 3's transcript = pair 2's + `transcript_entry(2, "patch", &format!("patched (lens: {lens_name})"), patched_contents)` where `patched_contents` comes from the real `land()` and `lens_name` from the real lens (`python`→`PythonLens`, else `PlainText` — the same selection the fixture validator uses). Completions are the exact `<action>` texts above, ending at `</action>`, no trailing newline after the tag.

### Task 2: The task factory + contamination guard (Python)

**Files:**
- Create: `tools/flywheel/factory/__init__.py`, `templates.py`, `generate.py`, `contamination.py`
- Create: `tools/flywheel/tests/test_templates.py`, `test_generate.py`, `test_contamination.py`
- Create: `tools/flywheel/README.md` (how to run; the determinism rule)

**Interfaces:**
- Consumes: the `flywheel-tool` bin (path passed via `--tool`; the factory shells out one JSON line per task).
- Produces (Task 3 runs these CLIs):
  - `python3 -m tools.flywheel.factory.generate --seed N --count 1000 --tool <path> --out corpus.jsonl --report fingerprint.json` → corpus JSONL (one `{"prompt","completion","meta":{"task_id","template","lens","pair"}}` per line), fingerprint JSON `{seed, tasks_by_template, tasks_by_lens, pairs, dedup_dropped, corpus_sha256, val_split_ids}`.
  - `python3 -m tools.flywheel.factory.contamination --corpus corpus.jsonl --gate crates/bloomery-daemon/fixtures/codec-tasks-v1.toml --out contamination-report.json` → exits nonzero on ANY overlap.

**Binding rules (each carries a test):**
1. **Templates** (`templates.py`): ≥8 python template families (wrong comparison operator, off-by-one index, off-by-one range bound, wrong constant/multiplier, inverted boolean, wrong variable reference, wrong f-string field, wrong dict key) and ≥5 plaintext families (config value, port/host mismatch vs surrounding lines, version/date string, wrong name in prose, wrong URL/path in docs). Each template is a pure function `(rng) -> Task{name, lens, target, files, goal, search, replace, summary}` drawing identifiers/values/domain nouns from word lists — NO literal reuse of codec-tasks-v1 vocabulary: the word lists must not contain any target filename, function name, or domain noun used in the gate set (enumerate the forbidden list in `contamination.py` and import it in `templates.py` so the tests can assert the lists are disjoint at build time).
2. **Structural validity** (mirrors the gate set's own validator, tested): `search` appears exactly once in the target; target among files; goal contains the target filename and ends with `Patch the file, then emit done.`; targets 5–60 lines; `search != replace`.
3. **Determinism**: `--seed N` twice → byte-identical corpus (test with a small `--count 6`).
4. **Verification**: every task goes through `flywheel-tool trajectory`; `landed:false` ABORTS generation with the task printed (a factory bug, never dropped silently).
5. **Dedup**: normalized (whitespace-collapsed, lowercased) `(goal, target_contents)` uniqueness; drops counted in the fingerprint.
6. **Validation split**: 5% of task_ids (deterministic from seed) marked in the fingerprint; the training task filters them out of the train set and monitors loss on them.
7. **Contamination comparator** (`contamination.py`): parses the gate TOML (stdlib `tomllib`); fails on any of: exact or normalized match of goals, file contents, target filenames, search strings; OR ≥0.8 Jaccard token-set similarity between any corpus goal and any gate goal (the near-duplicate net). Its own test plants a disguised copy of a gate fixture and must catch it (mutation-style: weaken the check → test fails).
- [ ] **Step 1: Write the failing tests** for rules 1–7 (pytest; the generate tests may use `--count 6` and a stub tool script that echoes canned responses, EXCEPT one integration test that uses the real built bin).
- [ ] **Step 2: Run to verify FAIL** (`python3 -m pytest tools/flywheel/tests -q`).
- [ ] **Step 3: Implement** (templates ≈ the bulk; keep each file ≤400 lines, split template families across modules if needed).
- [ ] **Step 4: Tests green; also `cargo test --workspace` still green** (no Rust changes expected — confirm).
- [ ] **Step 5: Commit**: `feat: flywheel task factory — seeded templates, structural validity, contamination guard (spec §3)`
